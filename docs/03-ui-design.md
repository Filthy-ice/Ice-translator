# 界面设计 — 全量模式与简洁模式

本文件的"控件清单"是 P4/P5 人工走查的对照表：走查时逐行勾选，位置或命名与本表不符即为缺陷。

## 1. 通用规则

| 项 | 规定 |
|---|---|
| 基准字号 | 14px；`font_scale` 乘以全局缩放（0.8~2.0）。**2026-10-28 变更 H 起，两栏正文在 `font_scale` 之上再各乘一档**：`source_font_scale` / `translation_font_scale`（各 0.8~2.0，默认 1.0），设置页外观分区各有滑杆；实现集中在 `theme::PaneText`，全量源文/译文与简洁输入带/译文带四个调用点共用同一处 |
| 中文字形（2026-10-28 补，变更 H） | 界面中文**固定落在黑体-简**（`/System/Library/Fonts/STHeiti Medium.ttc` 的第 **1** 面，`fonts::install` 装成 `Proportional` 首族、在 `Monospace` 里排在 Hack 之后以保持拉丁等宽）。此前由系统逐字符解析，本机落到苹方，用户原话"字看上去有点发灰不舒服"——**这一条只换族，一个颜色都没动**（配色属尚未开工的主题包 #28）。文件读不到时回落系统解析并记 debug，界面照常可用 |
| 字距与行距（2026-10-28 补，变更 H） | `config.ui.letter_spacing`（0~4px，默认 **0.5**）与 `config.ui.line_spacing`（0~16px，默认 **3.0**）作用于四个正文调用点，**默认档不许是用户抱怨的那个样子**，所以两项出厂非零。egui 0.37 没有单一入口：行距走 `Spacing::extra_text_line_spacing`（只有 TextEdit 自动吃）+ 每个 section 上的**绝对** `line_height`（传小了字形会被裁），字距要手工挂 `format.extra_letter_spacing`，TextEdit 那边只能经 `.layouter(...)` 塞进去 |
| 栅格 | 8px 基准间距；容器内边距 16px；控件间 8px；分组间 16px |
| 对齐 | 标签左对齐，数值/状态右对齐，按钮文字居中 |
| 焦点环 | 键盘焦点可见（1px 描边），Tab 顺序与视觉顺序一致 |
| 主题 | **默认跟随系统深浅色**（`ThemePreference::System`，egui 侧即默认值，系统切换后下一次重绘跟随）；设置里提供三态单选：跟随系统 / 强制浅色 / 强制深色，选择即时生效并写入 `config.ui.theme`（2026-10-28 变更 J 起，这三态在**两种形态的右下角各有一颗左右推动的滑块**——同一条 `views::theme_switch`，见 §2 F-18 与 §3 K-12；两处写同一项，生效仍只在 `theme::apply`）。主色用于"翻译"主按钮，错误用红、降级提示用黄 |
| 控件边框（2026-10-28 补，用户原话"浅色模式下应该有黑色边框，深色模式下应该有淡灰色边框。浅色鼠标放上去下陷整体变深颜色，深色鼠标放上去颜色变浅"） | 三态（未激活/悬停/按下）各配 1px 实线，颜色唯一出处是 `theme::edge_color(dark)`：深色 `gray(120)`、浅色 `gray(30)`。根因是 egui 亮色主题下 `widgets.inactive.bg_stroke` 本就是 `Stroke::NONE`（`style.rs` 的 `Widgets::light()`），按钮只有一层灰底没有边框，悬停才浮现一条线。悬停/按下同时做**负 `expansion`**（纯绘制层内缩，不参与布局，看起来就是按下去了一点）+ 底色变深（浅色 ×0.8 / 深色 ×1.55），按下再深一档。**栏子的分隔线不走这一处**：`Panel` 自己在靠正文那一侧画一条（`show_separator_line` 默认开，取 `widgets.noninteractive.bg_stroke`），工具条与底栏因此天然同色（详见 §2 的 A 那条 2026-10-28 补）。**幂等**：这套改动每帧都跑，必须重复应用结果不变（`widget_contrast_is_idempotent_across_frames`） |
| 失焦半透明（2026-10-28 改，FR-3.7） | 简洁窗失焦时**整窗**不透明度降到 `config.ui.unfocused_alpha`（`0.30..=1.00`，默认 0.85，设置页滑杆即时生效并持久化），走原生 `NSWindow.setAlphaValue`，标题栏/边框/红绿灯一起变淡；代价是正文文字同样变淡。拿不到原生层（非 macOS、无句柄、不在主线程）时退回只淡窗内底色的 `apply_dim` |
| 应用图标（2026-10-28 补） | Dock 磁贴用 2026-10-27 定稿的 `assets/icon/icon-1024.png`（蓝色圆角方块 + 白「文」气泡 ⇄ 蓝「A」气泡，四角透明），`include_bytes!` 随二进制编入、启动时降采样到 256 见方后交给 `NativeOptions::viewport.icon`。**这一项不设的话 Dock 显示的是 eframe 自带的 egui logo**，与"资源放对了没接线"是两回事；细节与平台差异见 `05-dev-guide.md` §8。Dock 上那行**名字**仍是二进制名 `ice-translator`，改它要做真正的 `.app` bundle（未做） |
| 提示条（2026-10-28 变更 I 重写，2026-10-29 变更 L 改时长） | **一律是窗口正中的浮层，`TOAST_LIFETIME` 内线性淡出后自己消失，没有关闭按钮、点它也不关**（用户原话"所有的提示类弹窗都是中心弹窗500ms内淡化消失，不应该有关闭的操作和按钮。"，同日改判"所有弹窗改为1s淡化消失吧，500ms太短了"）。三条实现口径：① 锚点 `Align2::CENTER_CENTER`（`views::toasts`，无头断言量到中心的偏差 ≤1px）；② 时长与淡出共用一个数 `TOAST_LIFETIME = 1s`（变更 I 定的是 500ms，变更 L 抬到 1s；`Toast::opacity()` 与 `expired()` 都从这**同一个**常量推导，所以那次改判只动了这一个字面量，名字里也不带时长），`Toast::opacity()` 给线性不透明度，`Frame::multiply_with_opacity` 一次处理底色/描边/投影，文字色另走 `gamma_multiply`；③ **`Area::interactable(false)`**——浮层不进命中测试，压在按钮上时下面那颗照样点得到（原来那颗 `×` 会拦掉一整块按钮）。淡出要人看见就得有人逐帧来：屏幕上有提示条期间以 `TOAST_FADE_STEP = 16ms` 请求重绘（1s 约 60 帧），提示条一空就回到 NFR-2 的空闲策略，TC-N-1 那条 30s cputime 测法不受影响。**随之作废**：`dismiss_toast`、那颗 `×`、右下角偏移 `TOAST_OFFSET`（P4 缺陷 D-5 那次把 `×` 移到文字同一行，这一整颗现在不存在了）。**`confirm()` 不在这条里**——它要的是用户做一个决定，自动消失等于替用户答"否"，那两颗按钮留着 |
| 空态 | 未翻译时译文区显示灰色提示"输入后按 Enter 翻译"，不显示空白 || 加载态 | 主按钮变spinner+"翻译中…"并禁用重复提交；已有旧译文时用右上角细条提示"更新中"，不清空正文 |
| 破坏性操作 | 清空历史需二次确认 |
| 文案 | 简体中文；按钮用动词开头（"复制译文"而非"译文"） |

## 2. 全量模式布局（默认 1080×720）

│  │ 多行编辑器               │  │  │ 只读展示（等宽衬底，可选中）          │  │
│  │ 占位：输入或粘贴文本     │  │  │                                       │  │

│ E 动作底栏（**自占一行**，v0.7 REQ-013）                                      │

├────────────────────────────────┴─────────────────────────────────────────────┤
│ D 状态条 (28px)  就绪 · 机翻可用/AI 未配置 · 历史 42 条 · Cmd+Enter 翻译     │

> **2026-10-27 变更 D（CHG-004 v0.7 / Q-018、REQ-013）**：E 这条原来是**浮在译文框右下角的动作条**（不参与布局，靠正文末尾垫一条等高空白躲它），用户要求"把右下角那几个按钮放在右下边框？和翻译多少字在一行？"并补一条硬约束"要注意按钮边框和软件里的框不要冲突或者覆盖，如果不行就把按钮调整小一点"。现改为**自占一条底栏**：字数统计与动作按钮同一行（计数左、按钮右），底栏按自然高度参与布局，两栏正文拿到的矩形就是"扣掉底栏"那块——"最后一行被按钮挡住"从结构上不成立，`bar_cover` 那套预留连同它的断言一起作废。空间不足的退让顺序固定为：**先降按钮尺寸一档**（84×28 → 64×28，只降宽度不降高度）→ **再换行**（底栏随之长高，正文跟着让）→ 字数文本可省略号截断，**按钮永远不裁掉、不压框**。同批：字数行从 B 栏脚注搬进 E，B 因此没有页脚；两栏是否等大改量**两个滚动容器的矩形**（等高、顶边对齐）。

> **2026-10-28 补（缺陷 D-11，仍属 REQ-013）**：E 这条由 `views::show` 在**窗口层**建，顺序固定为工具条 → 状态条 → E → `CentralPanel`（`CentralPanel` 会吃掉剩余矩形，排在它后面的 `Panel` 收不到位置）。第一版把这条 `Panel::bottom` 留在了 `CentralPanel` 里面，而那层的默认框架四边各 8px 内边距，于是按钮的上下留白成了**上 7、下 15**（用户 2026-10-28 原话"按钮上下留白距离不同"），条子两侧也各少 8px。现在 E 横满整窗、下沿贴住 D 状态条，按钮上下各 `BAR_MARGIN`=6px，条子顶部那 1px 是 `Panel` 自带的分隔线。**同批第二条**：E 到了窗口层就得自己画底色（`.fill(panel_fill)`）——它下面不再被 `CentralPanel` 的 `panel_fill` 盖着，而 eframe 的默认 `clear_color` 是半透明深灰，留空等于在窗口上开个透出桌面的洞。

> **2026-10-28 补（F-10 状态行搬出译文框，缺陷 D-15）**：耗时/缓存/分段/检测原来是**译文框内部**的一排胶囊徽标（同日早些时候为消掉"两个框下面空白太多"从框外挪进框内），用户看到实物后退回——"**状态怎么又放译文框里了？里面非要有东西你才不难受吗？**"。现在 C 框里只有译文，徽标整排作废、改成 **E 底栏左端那一行文字**（`bar_meta`，片段 + 颜色：`缓存` 绿、`更新中` 黄、其余次要灰），顺带消掉重复：字数与徽标曾各写一遍"检测：xx"。左格宽度从 `CHAR_SLOT`=160 改成 `META_SLOT`=300（要装下"字数 18000 · 1583ms · 分 3 段 · 检测：简体中文"），仍可省略号截断，按钮那侧不退让。空白问题不再靠"挪进框里"解决：框外本来就没有第二条栏要躲，E 自占一行紧贴框底。**这条搬动让正文可视区到底栏之间的预算收紧了 29px**（`PANE_FOOTER_HEIGHT` + 行距一并作废），滚动测试按新预算断言，页脚若复发立刻可见。

> **2026-10-28 补（A 工具条的高度与边界感，用户第 2、3 条走查）**：A 原来把高度**钉死在 56px**，而那一排控件（页签 + 两个语言下拉 + 引擎单选 + 「悬浮窗」按钮）实测需要约 61px，钉死的结果是**换行**——工具条实际占到 82px，正文框上沿被顶下去一大截（用户原话"明明只占用一行，但是好远"）。现在 A 不再钉高度，按自然高度参与布局，`inner_margin` 上下各 `TOOLBAR_Y_MARGIN`=6px，实测正文框上沿 ≤64px（回归锁 `the_toolbar_takes_one_row_so_the_panes_sit_right_under_it`，断言里带着"钉死 56px 那一版是 82px"这个数）。**边界感**：A 与正文的分界**只有 `Panel` 自带的那条下沿分隔线**，与 E 底栏同一条代码路径、同一个颜色（`widgets.noninteractive.bg_stroke`）。第一版（同日 D-13 之前）在这里额外套了一圈 `edge_color` 的 1px 边框，用户看着截图当场退回——"太明显了，突兀，和底部栏的分割线一样颜色就行，而且两侧不需要线条"，于是整圈 stroke 作废；"界限不明显"的真凶是栏高囤积把正文顶下去 26px，不是少一条线。回归锁 `the_toolbar_separator_matches_the_bottom_bar_and_has_no_frame`（同时断言顶区只有一条横贯整窗的线、它与底栏那条同色、顶区没有整宽的描边矩形）。

> **2026-10-28 变更 J（用户走查第六轮，接在 I 之后）**：**E 底栏最右端多了一颗主题滑块**（新格 F-18），用户原话"**而且全量界面也要有这个开关，不需要提示，看到的人都懂。也在右下角。**"——这句里的"右下角"对全量窗就是这条底栏的右边缘，和简洁窗那一颗是**同一个函数**（`views::theme_switch`），不是两套画法复刻两遍。它是 `right_to_left` 子带里**第一个**排入的控件，于是落在整条栏最右；`bar_layout` 拿到的可用宽从此要**先扣掉它**（`META_SLOT` + `THEME_SWITCH_W` + 一个 `BAR_SPACING`），否则按钮会排到滑块底下或溢出窗口。滑块不响应底栏那条"先降一档尺寸再换行"——它是定宽 40px 的自绘控件，没有文字，字号缩放不动它，退让全由按钮那侧承担。**没有悬停提示、没有任何文字**（用户那句"不需要提示"），三态只靠滑块盖住哪一侧、露出哪一侧来表达。**停止条件**：这颗滑块在真机上是不是"看到的人都懂"，只能由走查判（W-2.35）；若用户看不出左右含义，回退方案是在两端各加一个文字标签——那要用户裁定，不自行加。
>
> **2026-10-28 变更 I（用户走查第五轮）**：这一节的窗口顶部**还有一条系统标题栏**（此前只在 §3 画过，全量窗共用同一个原生 `NSWindow`，没单独登记），它的最右端当时多了一颗**图钉 = 置顶**（§3 K-09 是同一条，两种形态一次装配都有）。用户那句是明确点名的："**全量界面也要有**"。全量窗此前界面上根本没有置顶入口——只有设置页外观分区那一格「始终置顶（Cmd+Shift+P）」和快捷键，这一颗把它补成了肉眼可见的；那颗文字开关在简洁窗动作行里就此删除，所以**全量窗的置顶入口是净增，不是搬动**。**位置于 2026-10-29 由变更 K 改判：图钉不在标题栏里了，两种形态都画在界面内**（下面那条）。
>
> **2026-10-29 变更 K（用户走查第七轮，接在 J 之后）**：**图钉从原生标题栏挪进界面**。用户是在真机走查里先问"图钉？哪来的图钉？让你加也没见你加啊"，看清之后给出位置："**全量窗挪动到精简（悬浮窗）两个字左侧，悬浮窗状态下，放在（右下角）颜色切换左边**"。这两个位置都在窗内，而原生那颗只能挂在标题栏**最右端**（`addTitlebarAccessoryViewController` + `setLayoutAttribute(Right)`，egui 画不进 `NSTitlebarView`），满足不了这句——于是 `system::pin` 整个模块删除，改由 `views::pin_toggle` 这一个函数在两处各调一次：全量窗 A 工具条那条 `right_to_left` 带里排在「悬浮窗」之后（因此落在它左边），简洁窗 E 动作行右下角那条 `right_to_left` 子带里排在滑块之后（因此落在滑块左边）。**行为一条没变**：仍是单点即切、置顶 = 实心摆正 + 强调色、未置顶 = 空心斜 45°，落地仍只置 `Effects::toggle_topmost`，与 `Cmd+Shift+P`、设置页那一格同一条通道（K-09、TC-3.4）。**连带的两处几何**：① 标题栏双击的命中带右端不再让开那 28px，只留一道 `EDGE_PAD`（F-19）；② 简洁窗动作行行内把手的右端从"滑块之前"改成"图钉之前"，图钉那一格经 `drag_probe` 验过不触发拖拽（K-01）。**宽度度量随之从 262px 回到 296px**（§3 末段），`MIN_COMPACT_W` 仍是 400。

### 吸附与悬停唤出几何

```
边界矩形 = 所有显示器可见区的并集（screen::desktop()，逐屏去掉菜单栏与 Dock 后取并集）
        —— 不是"窗口所在那块屏的可用区"：两块并排放的屏中间那条接缝不是桌面的边，
           按单屏算会把窗口藏进接缝，热区收不到悬停、也量不出向内位移（2026-10-27 缺陷 D-8）。
           离屏校验（FR-3.6 的夹回）仍按单屏可用区，那条问的是"这块屏上看不看得见"。
"松手"怎么判（2026-10-28 缺陷 D-16）：原生拖拽进的是 AppKit 的嵌套事件循环，鼠标抬起那一下不投递给本应用，
   egui 的按键状态在整段拖动期间是旧值。所以每帧先问硬件掩码（+[NSEvent pressedMouseButtons] 的位 0）：
   还按着 → 一个结论都不下，静止计时重新起算（按住多久窗口都不许动）；
   已抬起 / 问不到（非 macOS、非主线程、无头） → 再等窗口 rect 连续静止 150ms 才定案。
定案时的窗口 rect，只量左右两条边：
   d_left  = window.x - area.x
   d_right = area.right - (window.x + window.w)

若已停靠在左/右（锚点 = 停靠那刻下发的窗口原点，是独立状态；不能取每帧被 capture 改写的 compact_rect）：
   沿停靠轴向屏幕内的位移 ≥ snap_threshold_px(40) ──► docked_edge = None，位置原样保留（拖离）
   —— 拖离不能共用 d：藏出去后窗口在停靠轴上本就超出可用区一整个自身宽，
      d 恒为大负数，用它会每次吸回、拖离永远不成立

否则若 min(d_left, d_right) < snap_threshold_px(40)：
   右： rect.x = area.right - sliver(3)     docked_edge = Right
   左： rect.x = area.x - rect.w + sliver    docked_edge = Left
   上/下：不吸附（v0.5 起取消——藏进菜单栏/Dock 后悬停唤出不成立）
否则 docked_edge = None（自由浮动）

悬停唤出（停靠态，收起中）：
   指针进入那 sliver 的窄边 ──► 立刻整窗唤出（不补间）：右 x = area.right - rect.w / 左 x = area.x
                               docked_edge 不变，停靠态层级置为浮于其他应用之上
   指针离开窗口 ≥ 500ms     ──► 收回原位；正在窗口内按住（拖窗/选字）或输入框有焦点时不收回
   收回后指针仍压在那 sliver 上 ──► 不许立刻再弹出（闸门：指针先离开创口带再一次进入才算下一轮）
   刚吸附落位时同样置闸门      ──► 否则"拖到边上松手"会当场弹回来，看起来像停靠没生效
```

贴边后**只藏左/右**：窗口藏到那条边之外，可视区内只留 `dock_sliver_px`（默认 **3**）宽的一条热区，且它恒在屏幕最外沿——光标推到边里必然落进去，"错过它"在几何上不可能，这就是悬停唤出的前提。停靠态无论用户的置顶偏好如何都浮在其他应用之上，否则那 3px 被盖住就收不到指针事件（2026-10-23 走查实证）。夹取只处理非预期的越界：交叉轴全量夹回可视区，停靠轴仅在窗口沿该轴比可用区还长时把起点夹到 `area.min`。`sliver` 与 `threshold` 均可配置并被 `sanitize()` 夹在合理范围（`sliver` 2~24）。

> 2026-10-23 变更 A（CHG-004 v0.4 / Q-009）：本块原来的右/下两行写的是 `area.right - rect.w + sliver` 与 `area.bottom - rect.h + sliver`，与左/上不对称（算出来是窗口基本全可见、只往外多探 6px），也与"保留可见热区供拖回"相反，故改为四边对称版；连带把拖离判定改成"相对停靠锚点的位移"。
> 2026-10-23 变更 B（CHG-004 v0.5 / Q-010，**推翻变更 A 的四边对称**）：用户真机试了一次停靠就把窗口弄丢了（藏出去只剩 6px 窄边、那窄边因另一处缺陷是 6×422、`always_on_top = false` 时又被别的应用盖住，而唯一的召回手段"停靠指示"按钮自己在屏幕外）。现改为：**只认左/右两条边、热区 3px、鼠标悬停自动唤出、离开自动收回、K-07 的按钮机制作废**。同批把动作行改回正常字号（放不下换行）并把窗口默认/下限高度抬到 130px，另修"切换形态时 `capture` 把待生效尺寸冲掉"的缺陷（D-6）。
> 2026-10-27 变更 C（CHG-004 v0.6，走查三项修正）：① 简洁窗改带原生标题栏、顶部把手条删除、窗内把手减为两处，吸附判定改由几何跳变观测补上（Q-013，见 K-06 与 §3 顶部图）；② 输入行按内容长高到三行封顶、清空退回原高度（Q-014，见 K-01）；③ 吸附/停靠/唤出的边界矩形从"窗口所在那块屏的可用区"改为**所有屏可见区的并集**，两块屏相接的接缝不再算边（缺陷 D-8，见上面伪代码首行）。同批修掉"长译文滚到底最后一行看不见"（缺陷 D-9）：简洁窗是滚动容器的默认 64px 最小视口把矮栏视口抬出框外，全量窗是右下角浮层动作条盖住正文末行——两处的修法分别写在 K-02 与 `02-architecture.md` §3.3，判据落到走查表 W-2.24。

### 形态切换（FR-3.9）

切换不是"关一个窗再开一个窗"，而是同一个窗口一次性改几何，**不做补间动画**：

```
全量 rect(F) ── 一帧 ──► 简洁 rect(C)      （反向同理）
下发顺序（同一帧内，一次性）：
  Decorations(目标形态)  ── 原生属性，只能整段设一次，逐帧设会闪
  InnerSize(目标尺寸)
  OuterPosition(目标位置)
期间：置顶层级恒定；内容（源文/译文/语言对）不动；不发起任何翻译请求；
      切换完立刻可交互，没有"动画中"这个状态。
```

> **2026-10-22 变更**：本节原为"180~220ms ease-out 形变动画"（0-35% 每帧一次 `InnerSize`、35-60% 淡出、60-100% 淡入）。真机实测（`features/CHG-004/evidence/T-001-hypothesis-verdicts.md`）证明逐帧 `InnerSize` 在 macOS 上不可用：200ms 里只有 4~5 次请求落到窗口，并复现 ~1.0s 事件循环停摆，观感是"一卡一卡的 PPT"；改用"窗内补间"（窗口先变成两端外接矩形、只插值画在里面的内容矩形）实测丝滑，但用户看过后决定**取消动画**，两个方向都做成瞬时切换。因此 `ice-app::mode::Morph` 不再实现，本节只保留"同一窗口、一次性设几何、不黑屏不闪烁"的约束。

实现约束：几何命令由 `ice-app::mode` 在切换时一次性下发（见 `02-architecture.md` §3.3），切换后立刻 `mode::capture` 回读真实几何并落盘（SIGTERM 不走 `on_exit`，只靠退出保存会丢位置）。

### 标题栏双击：铺满 ↔ 还原（任务 #25，2026-10-28）

```
[全量窗] 双击标题栏空白处 ──► 内尺寸 = 当屏可用区 − 当帧实测的装饰厚度（本机高 32pt、宽 0）
                              原点 = 可用区的左上角（菜单栏下面，不是 (0,0)）
        再双击一次      ──► 回到 full_rect 记着的那组几何（铺满期间不覆写它）
```

- **观感定义**：铺的是**可用区**（`NSScreen.visibleFrame`，去掉菜单栏与 Dock 那块），不是整块屏幕。用户说的是"铺满整屏"，这里按"最大化"的通行含义落地：菜单栏（原生窗口层 24）与 Dock（层 20）合成在本应用窗口（普通层）之上，铺成整块 `frame` 会让我们自己那颗红绿灯被盖住一截——观感是窗口坏掉，不是最大化。**这一条属"实现替用户做了判断"，走查 W-2.37 若判定要的是连菜单栏底下那条也盖住的整屏尺寸，改的是 `mode::fill_size` 的目标来源，不是再加一个开关**。
- **命中范围**：只有标题栏的**空白处**算——左右各让开 6px 边距，左端让开红绿灯（按 `standardWindowButton(...).frame()` 实测的最右缘），右端只剩那道 `EDGE_PAD`（图钉原先占的那 28px 让位区随 2026-10-29 变更 K 一起删除：那颗图钉已挪进窗内工具条/动作行，标题栏右半再没有会收点击的东西，见 `02-architecture.md` 的 `system::dblclick` 行）。单击、内容区、窗口其余部分一律原样交给系统；拿不准就不吞（宁可由系统去做它在"系统设置 → 窗口 → 双击标题栏"里配的那个默认动作，通常是最小化）。
- **已知代价（用户需知晓）**：**双击之后立刻按住拖动**这条路失效。第二次按下的那一下被我们吞掉了，AppKit 的窗口拖拽循环因此没有开始；要拖动就松手后重新按下再拖。这是本地事件监视器（`+[NSEvent addLocalMonitorForEventsMatchingMask:handler:]`）这一条唯一可行路径的固有代价，登记在 `05-dev-guide.md` §8。
- **不与吸附/停靠互相打架**：只在**全量形态**安装。简洁窗的位置归吸附与停靠几何管，双击把它整屏化之后那 3px 热区就不存在了，悬浮条会再也唤不出来。
- **与「记住位置尺寸」（FR-3.6）的关系**：铺满期间应用不把手动缩放/拖动写进配置，`full_rect` 保持铺满之前的那组值，所以还原有源、重启后窗口也不是整屏。反过来说，**铺满状态本身不会被记住**——重启回到的总是"用户上次正常用的那个大小"。

## 5. 走查表使用说明

P4/P5 验收时按下述步骤做，结果与截图存入 `docs/evidence/`：

1. 按第 2/3 节的控件清单逐条对照实际界面，记录"存在 / 位置符合 / 行为符合"三列结论；
2. 空态、加载态、错误态各截一张图（错误态用故意填错的 Key 制造）；
3. 缩放窗口到最小允许尺寸，确认无控件被裁掉或重叠；
4. 亮/暗主题各截图一次；
5. 键盘 Tab 顺序走一遍，确认与视觉顺序一致、无控件不可达。

截图入库规则（硬约束）：本机 `screencapture` 只能整屏采集，因此每张图必须裁剪到**只含本应用窗口所在矩形**，提交前逐张打开确认画面里没有用户其他应用的内容（代码、聊天、文档均算）；无法裁净的就不要提交，改记日志/文本证据。屏幕锁定时拍到的是锁屏壁纸，采集前先确认会话已解锁。
