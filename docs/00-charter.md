# 立项说明书 — Ice Translator

| 项 | 内容 |
|---|---|
| 产品名称 | Ice Translator（仓库名 `Ice-translator`） |
| 形态 | 桌面客户端，macOS 优先，Windows/Linux 可编译 |
| 实现语言 | Rust（唯一实现语言，不引入 Python 运行时） |
| 用户 | 开发者本人，单用户，无账号体系、无服务端 |
| 许可 | Apache-2.0（沿用仓库已有 LICENSE） |
| 文档目录 | `document/` → 软链到仓库内 `docs/`，单一真源 |
| 立项日期 | 2026-10-19 |

## 1. 为什么要做

日常读英文文档、论文和界面截图时，现有工具存在三个反复出现的痛点：

1. **词典类工具只有机翻**，遇到长句、专业表述、需要语气还原的内容质量不够；
2. **AI 翻译要来回复制粘贴**，没有一个常驻屏幕边、随取随用的入口；
3. **看到图片里的外文（截图、PPT、说明书）没有顺手的路径**：要么手动逐条敲进翻译框，要么把图上传到第三方网站，隐私不可控。

自己写一个客户端，把"文本双引擎 + 常驻悬浮 + 图片本地 OCR 与译文回填"合到一个进程里，是本项目唯一的动机。它是自用工具，不追求市场完整度，但要求每一条写进需求的功能都能被验证。

## 2. 目标（v1.0 交付定义）

| 编号 | 目标 | 衡量方式 |
|---|---|---|
| G-1 | 文本翻译双通道可用 | 同一输入在机翻/AI 两引擎下均能出结果，可一键切换 |
| G-2 | 常驻效率入口 | 简洁模式窗口贴边停靠、覆盖在其他应用之上、快捷键秒开 |
| G-3 | 图片翻译闭环 | 一张英文截图能在本地完成 OCR→翻译→生成替换后图片，无需上传原图 |
| G-4 | 全本地化配置与隐私 | API Key 存 macOS 钥匙串；图片处理全程不出机器；日志不记录原文全文 |
| G-5 | 工程可交接 | 需求/设计/开发/测试/验收五类文档齐备，每个阶段有可核对的验收结论 |

## 3. 明确不做的（Out of Scope）

写清楚边界，防止范围蔓延。以下项**不在 v1.0**，如需实现另立里程碑：

- **像素级完美版式复原**：渐变/纹理/照片背景上的文字擦除只用启发式修补，不集成 LaMa 一类的学习型 inpainting 模型。复杂背景走"覆盖层模式"兜底。
- **PDF 重排版**：PDF 内的矢量文字提取属于另一条技术路线，v1 只处理位图。
- **全局屏幕取词**：需要 macOS 辅助功能权限且实现不稳定，v1 只做应用内快捷键 + 剪贴板监听。
- **批量文档/整站翻译、术语库导入导出、多设备同步**。
- **移动端**。
- **Windows/Linux 的 OCR 原生引擎**：这两个平台保证能编译、能跑文本翻译；OCR 在 v1 仅 macOS 可用，其他平台明确提示降级。

## 4. 技术方向（详细论证见设计文档与 ADR）

| 层 | 选型 | 理由 |
|---|---|---|
| UI | `egui` / `eframe` | 纯 Rust、三平台一套代码、原生支持 `always_on_top`、无边框与视口命令，契合"双界面+置顶+贴边" |
| 运行时 | tokio | 网络 IO 与图像流水线异步化，避免 UI 卡顿 |
| OCR | macOS Vision（`objc2-vision`） | 系统内置、质量高、零下载模型、完全本地 |
| 图像 | `image` + `tiny-skia` + `ab_glyph`/Core Text | 纯 Rust 栅格化，中文与 emoji 字形回退可控 |
| HTTP | `reqwest` + rustls | 不依赖系统 OpenSSL，跨平台省心 |

## 5. 里程碑与阶段验收

八个阶段，每阶段结束**必须有验收结论并 commit + push**，验收不通过不得进入下一阶段。

| 阶段 | 交付物 | 验收门槛（简写，详见 `06-test-cases.md`） |
|---|---|---|
| P0 立项 | 立项书、需求文档 | 每条需求有编号、有可测的验收标准，无二义表述 |
| P1 骨架 | 工程结构、开发文档、可运行空窗口 | `cargo build`/`clippy` 通过，窗口能启动 |
| P2 设计 | 架构/UI/图像流水线设计、ADR | 每条 FR 能映射到具体模块，无孤儿需求 |
| P3 引擎层 | `ice-providers` + 单测 | 两引擎真实调用成功，网络故障路径可诊断 |
| P4 全量界面 | 主界面 | 截图人工走查，控件位置与设计稿一致，空态/错误态可见 |
| P5 简洁界面 | 悬浮条模式 | 置顶实测有效、四边吸附可用、切换不丢状态 |
| P6 OCR | `ice-vision` | 样图集 OCR 字符正确率达标并留档 |
| P7 回填 | 生成替换后图片 | 样图人工评分均分 ≥ 3.5，失败案例进已知限制清单 |
| P8 收口 | 测试用例、验收报告、release 包 | 需求追踪矩阵无空行，`cargo test --release` 全绿 |

## 6. 主要风险与对策

| # | 风险 | 影响 | 对策 |
|---|---|---|---|
| R-1 | egui 多视口在 macOS 上稳定性一般 | 双窗口体验崩 | 设计阶段即定为**单窗口双模式**（用 ViewportCommand 改尺寸/装饰/置顶），P5 优先验证 |
| R-2 | OCR 错字导致译文全错，且难自动评测 | 迭代慢、质量不可知 | 识别结果做成**可编辑**再翻译；建 8~12 张标注样图集，每阶段固定回归 |
| R-3 | 译文长度膨胀导致回填排版崩 | 生成图不可用 | 字号自适应 + 超出框则降级为覆盖层模式，不硬塞 |
| R-4 | AI 服务参数由用户自备，首次运行必失败 | 开箱体验差 | 机翻通道零配置可用；AI 未配置时明确提示并引导到设置页，不静默失败 |
| R-5 | API Key 落盘泄露 | 隐私事故 | 只存钥匙串，配置文件里只存引用；日志脱敏 |
| R-6 | 中文缺字形变豆腐块 | 生成图不可读 | 用 Core Text 取系统 CJK 字体，内置字体回退链并在 P7 专项验证 |
| R-7 | 自用项目容易失控膨胀 | 永远交付不了 | 第 3 节的"不做"清单为硬约束，加需求须先改本文档 |

## 7. 完成定义（Definition of Done）

v1.0 视为完成，需同时满足：

1. 需求文档中所有 P0 级（Must）需求有对应实现与通过的测试或走查记录；
2. `cargo test`、`cargo clippy -- -D warnings`、`cargo build --release` 三条命令全绿；
3. `docs/07-acceptance.md` 中每个阶段的验收结论为"通过"或"带已知限制通过"，且已知限制有明确编号；
4. 需求追踪矩阵（`docs/traceability.md`）每条 FR 都能填出"设计章节 → 代码位置 → 测试用例 → 结果"；
5. `README.md` 能让一台全新 mac 在 15 分钟内跑起来。

Should/Could 级需求未实现不算未完成，但必须在 `07-acceptance.md` 的"延期项"中列明。
