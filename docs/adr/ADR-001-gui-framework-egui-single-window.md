# ADR-001 GUI 框架：egui/eframe，单窗口双模式而非多视口

- 状态：已接受
- 日期：2026-10-19
- 关联：FR-3.1~3.8、NFR-5、NFR-7、R-1

## 背景

需要同时满足：全量窗口、可切换的窄条悬浮窗、始终置顶、拖拽贴边停靠、跨平台可编译、纯 Rust。

候选：

| 方案 | 置顶 | 无边框/贴边 | 跨平台 | 成本 |
|---|---|---|---|---|
| egui/eframe | `ViewportCommand::AlwaysOnTop` | `WindowLevel` + `Position` 可编程 | 三平台 | 低 |
| Tauri 2 | 有 API | 有 API | 三平台 | 引入 WebView 与前端栈，产物大、与"纯 Rust"目标冲突 |
| 原生 AppKit + objc2 | 最强 | 最强 | 仅 macOS | 无法覆盖 Windows/Linux，开发量最大 |
| Slint / Iced | 支持不一 | 需手写平台代码 | 三平台 | 学习成本与文档量不及 egui |

## 决策

采用 **eframe 0.37 + egui**，并且**全量模式与简洁模式共用同一个窗口**，通过 `ViewportCommand` 动态改变尺寸、装饰、层级与位置来实现两种形态；不启用 egui 的多视口（`open_viewport`）。

## 理由

1. 立即模式 GUI 让"同一个 App 结构体在两种布局下渲染"变成一次 `if` 分支，而不是两套窗口生命周期管理。
2. 多视口在 macOS 上的焦点、层级与退出行为长期存在不稳定问题（R-1）。单窗口方案下，置顶、贴边、失焦半透明都由同一组 viewport 命令控制，行为可预测、可被一条命令实测验证。
3. 模式切换需要保留源文、译文与语言对（FR-3.3）。单窗口天然共享同一份状态，不存在跨视口状态同步与丢帧风险。
4. 代价：全量界面与悬浮条不能同时出现在屏幕上。这是可接受的——两个模式的定位本来就是"专注翻译"与"随手一瞥"，而非并列使用。

## 影响

- 布局必须能在 460×96 与 1080×720 之间切换而不重新构建状态；所有绘制代码按 `UiMode` 分支。
- 窗口的 position/size 由 egui 上报给 App 状态，再由 App 依吸附规则回写，形成"拖拽→上报→计算→回写"闭环（见 `03-ui-design.md`）。
- 若未来确需两个窗口并存，应改用 AppKit 分支而不是回头折腾 egui 多视口。
