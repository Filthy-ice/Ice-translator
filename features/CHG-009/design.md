### 数据流（macOS 主路）

```
点「框选贴图」/ F1（全局）
  └─ Effects::capture ── 帧末 ── Job::ScreenCapture
        └─ spawn_blocking: screencapture -i -x -o -t png <历史目录>/<pid>-<自增>.png
              ├─ 文件出现 → Outcome::ScreenCaptured(path)  ─┐
              ├─ 文件没出现 → Cancelled（什么都不做）        ├─ 回信通道(有界) + request_repaint
              └─ 子进程起不来/被拒 → Failed(类别)  ──────────┘
                    ↓ 帧循环
        pin::open(path 的内存像素)              ← 只钉，不派翻译（REQ-001 末句）
              ├─ 顺带做一次历史老化（REQ-008）
              └─ 后台派发「只识别」任务 → 完成后文字层可选（REQ-005）
                    ↓ 用户按下带子里那颗「翻译」
        既有链：识别 → 翻译 → 回填 → 成品 → **原地替换这张贴图**（Q-008 默认 (a)）
                    ↓
        「复制」走 clipboard::write_image · 「保存」走 panel::request_save（CHG-006 T-010 现成接缝）
```

**框选与钉屏是两条动作，不是一条流水线**：v0.1 把它们串成一条（截完直接进图片页），v0.2 中间断开——断开的那一点正是他要按下的那颗按钮。

### 三平台四格（写进 `docs/05` §8 的那张表，批准前先如实标 待取证）

| 平台 | 取图 | 钉屏 | 全局热键 | 文字层与翻译 | 净效果 |
|---|---|---|---|---|---|
| macOS | `screencapture -i` → 我们指定的路径 | Deferred viewport，无边框置顶（事实 3/5） | Carbon FFI：注册面 noErr（事实 6）、**派发面 2026-11-06 真人按键证毕（事实 35，handler 落点见事实 36）** | Vision 本地 OCR（CHG-005 已实现） | **四格全做**，本包实现 |
| Linux（X11 / Wayland） | 候选 `import` / `gnome-screenshot -a` / `grim`+`slurp` / XDG 门户，**未取证**（H3） | **已知受阻**：Wayland 下 winit 的 `set_outer_position`/`set_window_level` 是空函数（早先跨平台核查实测）⇒ 位置与置顶都给不了 | 待取证；Wayland 无门户级方案 | **无后端**（`native_ocr_supported()` = false，静态核查钉住） | 本包不做。入口在原地但禁用 + 一句"这台机器"；**钉屏那一格先记"结构性受阻"而不是"待办"** |
| Windows | `ms-screenclip:` / SnippingTool 很可能只进剪贴板（H4） | 理论可（winit 的 `WindowLevel` 在 Windows 有实现），**未验证** | `RegisterHotKey`（Win32，理论无需 crate），未验证 | 同上，无后端 | 同上；本包只登记这条路径存在 |

**这张表的存在理由**：用户那句"逐步适配 linux 和 win"如果只落到"截图"那一格，会得到一个"能截屏、不能翻译、钉不住"的跨平台，那是更坏的意外。四格分开写，批准时看到的就是这一张。

### 开放点（写在这里是为了不偷偷决定）

1. **带子是窗口的一部分，不是浮在透明区上**（REQ-003）：观感上比 某截图工具 多一条窄带。选它而不是 `with_transparent(true)` 的理由是"透明 + 圆角 + 只有按钮那块可点"这一套要的是逐像素命中测试，egui 的 viewport 透明在 glow 后端上的表现本仓没用过；**先做出能用的，视觉那一步等他看完再说**。
2. **成品原地替换，原图留在历史**（Q-008 默认 (a)）：这意味着同一块屏幕内容存在两个形态（历史里的原图 / 贴图上的成品），F2 永远唤回原图。要把成品也写进历史就一句改口，但那会让"上一次截图"变成"上一次操作结果"，语义漂。
3. **文字层拖选是整个包里最不确定的的一块**（停止条件 6）：egui 0.37 没有"图片上按识别框拖选文字"的现成控件，需要自绘选区 + 命中块 + 拼接文本。排最后，做不出来就停下来报工作量而不是砍掉整包。
4. **`screencapture` 的取消判据已实测完毕（2026-11-05 当晚，H1 → 事实 14）**：esc 取消与成功选区**两条路退出码都是 0**，只有"目标路径出现文件"这一条能分开它们。代码里的判据就此定死成"文件是否出现 + 能否解出图像"，**不许再出现"退出码 0 当成功"的写法**；同时事实 24 定了另一半——路径不可写时交互层**不会提前报错**，所以发起前必须 `create_dir_all`，否则最坏的失败时机是"用户画完了才告失败"。
5. **贴图尺寸换算有一处真会错两倍**（事实 22 / H9）：今晚那块在线屏 `pixels_per_point = 1.0`，拖 280 点落 281 像素，看着"1:1"像是普遍规律；接内置 Retina 屏后 `screencapture` 落的是物理像素，**不除 ppp 就会把贴图做出两倍大**、文字层坐标整体错位。`pin.rs` 里那一处换算 SHALL 是唯一的除法出处（窗口尺寸、带子重算、文字层坐标三处都读它），走查 **W-5.7** 专测这一条。
6. **贴图窗的两条写法是 POC 用一次错法换出来的，登记在这里防止实施时"想当然"回去**：① `show_viewport_deferred` 只在第一帧调一次 → 窗口真的建出来了，下一帧就被 egui 以 `it was never used this pass` 删掉（事实 25）。所以 `pin.rs` 是"每帧把集合里活着的各 show 一次"，这条循环形状不是可选风格；② 带子收起只切 `band_open` 不发 `InnerSize` → 留一条 40 px 的死区，不画东西、不透明、照吃命中（事实 26，采样 `#080808`）。两条都属于"看起来能跑、量出来是错的"，无头断言各锁一条。
7. **托盘隐藏态起第一张贴图那一步已定死写法（H10 关闭，事实 30/31）**：解是 `request_repaint()` + 一次 `ViewportCommand::RequestPaintWhileHidden`——那一帧 `ui()` 在 ROOT 仍隐藏时照常跑，贴图当场建出来且画对，主窗全程 `onscreen=false`。原 (a)（先闪主窗）与 (b)（改 CHG-008 的隐藏做法，要走 `revise`）**都不必发生**，(c)（隐藏态不生效）本来就被 spec 禁掉。剩下的活只有两件：① 与 REQ-010 共用"从循环外叫回一帧"那一小段 helper（不许分写两套，也不许拧成同一套可见性切换）；② 那条命令**只保一帧**，凡是需要多帧的地方逐帧重发，不许写成"发一次就永久有效"。
8. **本轮两条环境账，登记在这里是为了别让它们冒充证据**（事实 34）：① 取证中途第二块屏上线（1920×1200，位于 x=-1920），期间贴图窗被系统挪过位、主窗甚至跑到第二块屏上——这**加强**了"位置要读 `outer_rect` 而不是自己攒一份"，但**也让事实 22 那块"唯一在线屏"变成局部条件**，H9（Retina 换算）仍未取证，两块都不是 HiDPI；② 有几轮出现来源没查明的 Escape 事件送进贴图窗（一次 8 张全中），我们的处理器按 REQ-004 把它们关掉了。**这条不算键盘验证**——W-5.2 的 esc／空格／右键仍要他本人在机器前按，因为"谁按的"没定位，不能反过来当"esc 通路已证"。

## REQ-001 实现与验证

**链路**：`views/image` 那颗「框选贴图」只置 `Effects::capture = true` → 帧末 `run_effects` 交 `state.submit_capture()` 出 `Job::ScreenCapture{id}` → `jobs` 在 `spawn_blocking` 里跑子进程 → `Outcome::ScreenCaptured{id, path|cancelled|failed}` → `apply` 判代后调 `pin::open(...)`。**"复用而不是新造"是这条 REQ 的全部实现风格**：取图那一段是新的，钉上之后每一步（识别、翻译、回填、复制、保存）都是 CHG-005/006 已经跑通的路。

**为什么回信绝不派发翻译**（他的第一句）：`ScreenCaptured` 那一支只做三件事——建贴图、老化历史、派发**只识别**。断言写成"这一支里 `Job::Translate*` 一个都不许出现"，而不是"翻译是 None"，因为后者会让以后有人"顺手加一句自动翻译"时测试还在绿。

**为什么不许在帧循环里等**（事实 12）：`screencapture -i` 阻塞到用户画完为止，可能 2 秒也可能 2 分钟；放在 `ui()` 里就是 CHG-005 那条"面板不许 `runModal`"的同一个错误换了个载体。回信 `try_send` + `request_repaint`，理由与面板回调一字不差（那一下点击属于系统框选层，不属于我们的窗口）。

**幂等与并发**：`capture_in_flight.is_some()` 时 `submit_capture()` 返回 `None`（第二次点击被忽略，不是"顶掉第一次"——顶掉会让用户看到一张他没画过的图）。

**验证**：无头——那颗只给意图不给路径、在飞时第二次派发返回 `None`、回信按代丢弃、回信结果建贴图而**翻译通道一条都不发**；真机——W-5.3 的"框选界面真出来了、画完真钉上了"。

## REQ-002 实现与验证

三态在 `CaptureStage` 里就是三个变体，**取消不是失败**：`Cancelled` 那一支不落提示条、不建贴图、不改 `image`/`ocr`/`composed` 任何东西（与面板 `Reply::Cancelled` 同一条纪律，CHG-005 已锁过一次）。

**取消的判据按事实 14 定（已实测，不再是假设）**：三态分岔写成一条有序的纯函数判定，出处只有 `capture.rs` 一处——
① **文件出现且能解出图像** ⇒ `Captured`；
② **文件出现但解不出图像**（0 字节 / 坏 PNG）⇒ `Failed`，SHALL NOT 当成"取消"放过，也不许当成成功；
③ **文件没出现 + 退出码非 0 或 stderr 非空** ⇒ `Failed`（权限那一档就是这个形状：本仓 D-28 那晚实测到过 `screencapture` 打 `could not create image from display`，那条**不写文件**，所以只看"没文件"会把它误判成取消）；
④ **文件没出现 + 退出码 0 + stderr 空** ⇒ `Cancelled`，什么都不做。
**退出码单独没有区分能力**（esc 取消和成功选区都是 0），所以它只能当第二路的辅助信号；判据顺序、以及"为什么不是退出码"这两句 SHALL 写进 `capture.rs` 的注释与 `docs/05`，不留"我们猜的是退出码"这种第二判据。另按事实 24，发起前 `create_dir_all` 是这条链的前置而不是可选优化。

**失败只给能行动的话**：三类（系统工具不可用 / 被权限拒 / 未知）共用一句"这台机器上截不出来；可以先用系统截图（`Cmd+Shift+4`）再点「粘贴」"——退路是既有的、真的能走通的那条（事实 9/10），不是客套话。

**"未发现文字"不新造一档**：REQ-005 那次后台识别出空结果时，贴图带子里显示那一格既有文案，状态行不新增变体（CHG-005 的 `RecognitionStage::NoText` 已经承担这句话）。

**验证**：无头——回信枚举三态各断一条（取消不建窗不清内容、失败只提示条、空图走 `NoText`），**再加一条今晚实测直接给出的用例**：`Captured`/`Cancelled`/`Failed` 三路的判定函数按上面 ①~④ 各锁一条（用临时目录造"空文件""坏 PNG""没文件"三种真实状态）；真机——W-5.3 读不读得懂。**H1 那一条已经从"待真机证"移出，今晚证完了。**

## REQ-003 实现与验证

**带子几何是纯函数**：`pin_layout(image_size, band_open, scale) -> {window_size, image_rect, band_rect}`。它是这条 REQ 唯一能被无头锁住的部分：带子在下方、展开时 `window_size.y = image.y + BAND_H`、收起时等于 `image.y`（**收起 = 窗口缩到图片本身**，不是"带子还在但透明"，否则图上会多一条不吃命中的死区）。`BAND_H` 是一个常量，旁边写"为什么是这个"（一颗按钮的高度加上下留白，与 E 区那排同源）。

**那个 `scale` 参数的来历是今晚新登记的一条（事实 22 / H9）**：`image_size` 传进来的必须是**点**而不是像素，也就是 `PNG 像素边长 ÷ 那张屏的 pixels_per_point`，而且**这一处除法是全局唯一出处**——窗口尺寸、带子重算、REQ-005 文字层的框坐标三处都读同一个换算结果，各自再除一次或都忘了除就是"贴图比框的大两倍"那种现场。今晚只能证到 ppp = 1.0 那一档（在线那块外接屏，拖 280 点落 281 像素），所以这条**列进真机走查 W-5.7**：接内置屏截一次，量贴图边长与他框的是不是同一块。无头侧给 `pin_layout` 补一条 `scale = 2.0` 的用例，断言窗口边长是像素的一半——**这条不声称证明了真机行为，只证明换算只用了一处**。

**那颗「翻译」画在带子里而不是图上**：这是 REQ-003 的全部争议点，实现上就是"按钮的 `Ui` 只在 `band_rect` 里活动"。测试断言写成"带子收起时那几颗的矩形落在窗口之外/宽度为 0"，而不是"看不见"——看不见的东西如果还吃命中就是隐形陷阱。**这条警告今晚拿到了读数**：不发 `InnerSize` 时那条收起的带子仍是窗口的一部分，采样 `#080808`（不吃绘制、照吃命中），发了以后窗口逐帧从 `512x400` 收到 `512x360` 再展回 `512x400`，**左上角一直锚在 420,280 不动**（往下收，不把图挪走）。所以"收起"的实现位置只有一处：`band_open` 变的那一帧发一次 `ViewportCommand::InnerSize(pin_layout(...).window_size)`，SHALL NOT 指望 builder（它只在创建那帧生效，事实 26）。

**成品原地替换**：`Pin` 里同时存 `原图纹理 id` 与 `成品纹理 id`，替换只换显示的那一个 id 并重算 `image_size`（成品尺寸 = 原图尺寸，回填链不改尺寸，所以这条重算是幂等的——写一条断言钉住这个"不该变"，将来回填改成裁剪尺寸时这条会响）。

**验证**：无头——`pin_layout` 的三档（展开/收起/成品替换）、带子里恰有四颗、失败分支保留原图纹理；真机——W-5.3 的观感（那条带子丑不丑、按钮在图外这件事肉眼确认）+ **贴图窗出图与几何这一档今晚已由仓外 POC 量过（事实 17：`layer=3`、`bounds=420,280,512x400`、图片/带子/按钮三层各自的采样色都对，分界正落在第 360 行），所以这条 REQ 从"窗口机制未知"降成"观感待走查"**。

## REQ-004 实现与验证

**四个动作各自落在既有通道上，pin.rs 不开第二条实现**：拖动这一档**今晚有了读数**——`with_movable_by_background(true)` 实测能把无边框子窗拖着走（探针 mode D：拖完那张的 bounds 从 200,200 变到 660,480，隐藏再回来仍落在 660,480，事实 32），`ViewportCommand::StartDrag` 那一档探针没测过。所以实现按**前者起步**，`StartDrag` 只在实测不跟手时作为备选（"选定后删另一档"这条纪律不变，两档都写在注释里）；**位置的唯一来源是 `ViewportInfo::outer_rect`**——它连系统自己挪的位都读得到（本轮第二块屏上线时同一张被挪过 450,250 → 1174,538 → 1052,290，每次都读对了，事实 34），所以记位置、隐藏后恢复、成品替换后重算三处都读它，SHALL NOT 自己攒一份坐标副本。esc = **把这一张从"还在 show"的集合里摘掉**（事实 25 实测的就是这条路：不再 show 它窗口自己就销毁，且只销毁那一张，主窗与进程都还活着——比"另发一条 `ViewportCommand::Close`"少一个状态，也少一处"命令发了但下一帧又被 show 回来"的自相矛盾）；空格 = 切 `band_open`（连带那一帧的 `InnerSize`，见 REQ-003）；`C` = 走 `Effects::copy_pin(id)` → 帧末调 `clipboard::write_image`（与图片页那颗同一个函数）。

**右键四项用 `egui::ContextMenu`**：菜单项在 `pin.rs` 一处声明（一个数组，长度 4），加第五项要改这一处并有断言挡着——他那句"只要四项"是要被钉住的，不是要被打折理解的。

**焦点而不是悬停当"选中"**：`ViewportInfo::focused` 是唯一判据（spec REQ-004 明写不许用悬停）。esc 与空格只作用于**有焦点的那张贴图**，所以多张同时存在时不会出现"按一次关掉两张"——**这一条今晚实测过**：三张贴图同时在、送一次 Space 只有最后建的那张记录到收到按键（事实 27），winit 那句 `canBecomeKeyWindow` 恒 true（事实 4）在无边框子窗上兑现了。**所以我们不需要自己写焦点路由**，只需要读 `focused` 决定那颗键落在哪一张。

**验证**：无头——意图矩阵（每颗键/每颗菜单项 → 哪条 `Effect`，含"带子收起时翻译不发任务""esc 只关焦点那张"）、右键项数 == 4 的那条断言、**外加一条"位置只从 `outer_rect` 读"的形状核查**（`pin.rs` 里不许出现第二份坐标累计）；真机——W-5.2 三格：**拖动跟不跟手**、**右键菜单点得中吗**、**esc／空格他本人按一次**。**"键盘到不到子窗口"探针证过（事实 27），但本轮另有几次来源没查明的 Escape 送进了贴图窗（事实 34 ②），所以键盘那一格仍算他没按过——不许拿"日志里出现过 received key"当"他按了"。** 同时"多张贴图同时在"已证到 **8 张**（事实 27/33），W-5.3 那格只看攒到上限时的代价与观感（H7 收窄后的那一半）。

## REQ-006 实现与验证

**配置**：`config.toml` 新增 `[hotkey] capture / pin_last / reopen` 三条（字符串形态 `"f1"` / `"cmd+shift+4"` 都可解析；解析函数是纯函数，录入 UI 只是把按键拼成这一个字符串）。默认值就是他报的三个，`sanitized()` 遇到无法解析的回默认并记一句**不含用户输入原文**的日志。

**注册**：`hotkey::apply(&Hotkeys) -> Result<(), HotkeyFailure>`，mac 分支手声明 Carbon FFI（事实 6 证注册面、**事实 35 证派发面**）。这些细节必须写在模块注释里，因为它们每一个都是本机量出来的、不是从文档抄的：
- **事件处理器 SHALL 装在 `GetEventDispatcherTarget()`**（事实 36）：物理按键的 15+6+21 次派发**全部**落在 dispatcher target 那份 handler 上，装在 `GetApplicationEventTarget()` 的那份一次都没收到——**连注册在 app target 上的那两把键也是 dispatcher 的 handler 收到的**。所以"注册目标选哪个"不重要、"handler 装哪"是死的；写错的那一版症状最坏：`RegisterEventHotKey` 返回 0、设置页显示成功、按下去永远没反应。
- **`EventTypeSpec` 的四个值 SHALL 按 SDK 抄**：类 `'keyb'`（`CarbonEvents.h:1339`）、种 `kEventHotKeyPressed = 5`（`:4693`，是整数不是四字符码）、参数名 `'----'`（`CarbonEventsCore.h:178`）、参数型 `'hkid'`（`CarbonEvents.h:376`）。**本包在这一格上翻过一次车**：旧探针写的 `'kkbd'`/`'hotp'`/`'dirt'`/`'hkey'` 全不存在，而 `InstallEventHandler` 对着一个永远不会发生的事件类型照样返回 0 ⇒ "注册成功 + 回调 0 次"被当成了"派发不通"，v0.5 之前那批读数因此作废（事实 35）。
- **两处 FFI 形状**：`GetEventParameter` 的参数顺序是 `(事件, 名, 型, 实际型出参, 缓冲区大小, 实际大小出参, 数据出参)`（`CarbonEventsCore.h:893`），写反不报错、只在派发时读脏；`_DispatchEvent` 在 arm64 的 HIToolbox **没有符号**（链接期就报 Undefined symbols），别照着旧 Carbon 书写"自己泵一次"。
- 返回码非 0 要**原样翻译成一句人话**，不许 `let _ =` 吞掉。本轮实测到的两种：**`-9878 eventHotKeyExistsErr`**（`CarbonEventsCore.h:152`）= 同一个 `(键码, 掩码)` 已经注册过了——事实 36 顺手量清了它的脾气：**唯一性是系统级按键+掩码去重，与 target 无关**，往第二个 target 重复注册同一把键就是这个码；`-9868 eventInternalErr` = 掩码不合法（`rightShift`/`rightOption`/`rightControl` 这些位在 Mac OS X 上不支持，`Events.h` 明写）。
- 主线程：`InstallEventHandler` 与 `RegisterEventHotKey` **都要在主线程**——**但"派发依不依赖主 run loop 在跑"这件事已经不需要假设了**：事实 38 量到窗口 `Visible(false)` 收起、`ui`/`logic` 停摆 122 秒之后，按下物理键事件**照样送到 handler**。所以派发面不靠我们的帧循环，H6 那一半到此闭合。
- 改完键 SHALL 先 `UnregisterEventHotKey` 旧的再注册新的；只注册不注销会在每次改键后多一套活着的绑定（而 `-9878` 那条实测也说明"重复注册同一把"根本通不过，注销不是可选优化）。

**回调必须自己叫循环（本轮新增的硬规矩，事实 38）**：Carbon 回调只做两件事——把一个 `Action` 塞进一个原子位（或既有队列）、**紧接着 `ctx.request_repaint()`**。实测对照：回调里不叫循环时，`FIRED` 到了但 `logic`/`ui` 仍停在 122 秒前（画面与状态都不动，用户读到"按了没反应"）；回调里叫一次之后 **104ms** `logic` 与 `ui` 同帧跑起来，跑完又睡回去——**所以既不需要、也不许为热键保留任何常驻心跳**（NFR-2 的空闲承诺原样保住）。这条与 D-21 是同一族病：**只在事件到来时改状态、不请求重绘的原生回调，都会犯**（托盘那颗犯过一次，热键这一颗不能再犯一次）。
形状上照抄 `system/tray.rs` 那一套（`CONTEXT: OnceLock<egui::Context>` + 原子位 + 主线程取），**不开第二条通道**：Carbon 回调送出的意图 SHALL 落进既有 `Action` 枚举的同一个分派。

**「固定」与「打开上一次」的语义**：前者把"最近一次框选但还没钉住的那块"钉住（没有就什么都不做，spec 明写）；后者从历史读最近那张原图并 `pin::open`（无历史 → 一句"还没有截图记录"）。两个都不新建第二条取图路径。

**隐藏态那一次按下要多做一步唤醒（事实 28 → 解在事实 30/31，写法已定死）**：POC 两组对照量出来——主窗 `Visible(false)` 且**一张贴图都没有**时，`ui()` 一帧都不跑（连 `logic()` 也因无人请求重绘而停），此时注册的 deferred viewport 起不来；而**只要还有一张贴图活着**，主窗即使隐藏，`ui()` 照旧跑，第二张贴图正常出现。后来那一轮把"怎么叫醒"也量了，结论是两条命令缺一不可：
① `ctx.request_repaint()` —— 把停摆的事件循环叫回来。**只发这一条不够**（实测：唤 6 次，`logic()` 心跳回来了 8 次，`ui()` 一帧没跑，贴图始终没建出来，事实 31）；
② `ctx.send_viewport_cmd_to(ROOT, ViewportCommand::RequestPaintWhileHidden)` —— 让那一帧**在 ROOT 仍然隐藏的前提下**真的跑 `App::ui`。实测那一帧里 `show_viewport_deferred` 就把贴图建了出来，窗口列表当场出现它（`layer=3 onscreen=true`），像素采样也对（图 `#1E5ADC`、带子 `#2E6FF2`），而主窗在唤醒前后都是 `onscreen=false`、之后每帧 `ViewportInfo::visible()` 仍读到 false（事实 30）。
**这条命令只保一帧**（egui 明写"Holds for one frame; send it again for another"），所以实现里 SHALL NOT 假设发一次就永久有效：需要连续几帧的地方（例如贴图建出来那一帧之后还要再画一帧）逐帧重发。
这一段与 REQ-010 的 `prepare()/restore()` 共用的是**"从循环外叫回一帧"这一小段 helper**（同一个函数，两处都靠它），**不是同一套可见性切换**——截图那段确实要动 `Visible`（正负对照见事实 32），热键这段明确不动它。原 H10 的 (a) 那条（先 `Visible(true)` 闪一下再收回）**作废**，(b)（改 CHG-008 的隐藏做法）因此不必发生，本包不动 CHG-008 一行。

**验证**：无头——解析与回默认的边界、三个键 → 三条 `Action` 的映射、"不与 `Cmd+Shift+3/4/5` 相撞"那条常量断言、注册失败走那条文案（`HotkeyFailure` → 文案纯函数），**加一条形状核查（事实 30 之后是硬的）**：隐藏态那段唤醒只允许出现 `RequestPaintWhileHidden` + `request_repaint`，源码里 SHALL NOT 出现"为了起贴图而对 ROOT 发 `Visible(true)`"；真机——**W-5.1 请他按一次三个默认键**（H6 的唯一判据，我按不出物理键），**W-5.9 请他按一次"主窗收起后"的那一下**（要看两件事：贴图出来了吗、屏幕上有没有多出主窗——机制我们已在探针上证过（事实 30），但**探针不是真应用**，那一条链里还夹着子进程与历史老化，所以这一格仍要他眼睛收一次）。

## REQ-007 实现与验证

**路径生成**是纯函数：`<历史目录>/<pid>-<自增>-<epoch 秒>.png`。自增而不是只用时间戳（同一帧内两次点击会撞，`Instant` 精度不是保证），撞了就是后写的覆盖前一张；**pid 进去**是为了两个实例（开发版与正式版并跑）不互相覆盖。

**"即读即删"的改判**：v0.1 写的是"识别读到内存后立刻删临时文件"。v0.2 不删——历史就是那条链的产物存放处（他第 6 句），所以 REQ-007 只保留三条边界：**只有历史目录**、**日志与文案不含文件名/OCR 文本**、**删除只由老化与「清除所有历史」触发**。这条改判要写进 `docs/07` 的变更登记，不能只体现在代码里。

**日志字段白名单**：尺寸、耗时、张数、失败类别。文件名本身可能就是用户内容（`IMG_20261105_报销.png`），与 `secrets::fingerprint` 那套"只记长度与哈希"同一条纪律。

**验证**：无头——路径唯一性（连点两次不等、两 pid 不等）、错误与日志文本不含该文件名（把文件名塞进断言的反向检查）、`./sdd scan`；真机——`ls` 历史目录证内容只有图片文件（W-5.6）。

## REQ-008 实现与验证

**目录**：macOS 用 `dirs` 既有的应用支持目录（`~/Library/Application Support/…/shots/`），非 mac 用平台等价物；**这个路径不是配置项**（可配到仓库里就等于把隐私边界交出去）。目录不存在时 `create_dir_all`，失败如实报，不退临时目录。

**老化是一个纯函数**：`retain(entries, now, DAYS=7, MAX=200) -> Vec<to_delete>`，输入是 `(路径, mtime)` 的列表。它有两个边界要分别钉住：`mtime` 恰好在第 7 天那一条不删（"7 天内"的字面读法）、第 201 张进来时最老那条被删。老化在发起新一次截图时顺带跑一次（不开定时器：每帧跑的循环里少一件事是好事，而且没人看的时候不需要老化）。

**「清除所有历史」**：一次调用删掉目录里的图片文件，返回删掉的张数给提示条（"已清除 N 张"）。它是**直接删**而不是标记——留一堆不可见的屏幕内容在盘上是最坏的一种"删除"。

**F2 读的是最近那张原图**：与老化共用同一个排序函数（取第一个而不是取尾部），这样"最近"在两处只有一个定义。

**隐私口径改写的落点**：`docs/01` NFR-3、设置页那句说明、`docs/07` 变更登记三处同一句话——"只落进这一专有目录，7 天自动老化，一键清除"。代码改了文案没改，等于偷偷扩了隐私面。

**验证**：无头——`retain` 的两条边界、清除返回的张数、路径不指向仓内（一条 `assert!(!path.starts_with(repo))`）、F2 的排序与老化一致；真机——W-5.6。

## REQ-009 实现与验证

**一处判定，三个用途**：`capture::capability() -> Capability{Interactive, ClipboardFallback, Unsupported}` 是全局唯一出处，视图置灰、`pin::supported()`、`hotkey::supported()` 与 `docs/05` §8 那张表都读它（与 `native_ocr_supported()` 同族形状）。视图里 SHALL NOT 出现 `#[cfg(target_os)]`——散开的 cfg 是"某平台编译不过"的温床。

**编译面的保证方式**：非 mac 那一支是**同签名**的门控版本（`ice-vision/src/ocr.rs` 就是这么写的，并有静态核查测试钉住），所以 Linux/Windows 上 `cargo check` 起得来是本包硬要求；但本机只有 `aarch64-apple-darwin` 一个 target，因此**编译级按 TC-P-7 的老规矩记"未验证"**，不许拿"源码扫描看起来对"当"三平台能编译"。

**验证**：静态（源码扫描那条测试 + clippy）+ 真机（非 mac 那颗禁用入口的说明，W-5.5）。

## REQ-010 实现与验证

**这一条的形状已由取证定死（T-001 那一格今晚跑完了，事实 32）**：`capture.rs` 暴露"发起前 / 结束后"钩子对（`prepare()` / `restore()`），`app.rs` 在派发前后各调一次，走 Q-003 的 (a) 那一档。实测读数是：主窗与两张贴图全部 `Visible(false)` 后，**同一条 `screencapture` 命令、同一坐标**从 `#DC1E1E` / `#1EC81E`（正是那两张贴图自己的色）变成 `#161616` / `#A9AAAC`（桌面），主窗那一格从 `#080808` 变 `#1C1D1F`；隐藏期间三张窗在窗口列表里都还在，`layer=3` 与 bounds 一字不变，只是 `onscreen=false`。⇒ **"原样回到发起前那一刻"不需要我们自己存几何**：可见性发回去，位置本来就在那儿（拖动过的位置也保住了，同一次实测里回到 660,480）。`prepare()` 记下的那一组因此只剩两样——**置顶状态**与**可见性**，"几何"那一栏实测是恒等，写进注释免得实施时以为要恢复坐标。比 v0.1 多出来的是**贴图窗也要过这一对**：`prepare()` 要能同时收起主窗与 N 张贴图。

**还有一条实测把"谁来叫醒"这件事定死了**（事实 31/32）：全部窗隐藏后进程**连 `logic()` 都不跑**，所以 `restore()` 不能由帧循环里的计时器发起——它必须由**截图子进程那条完成回调所在的线程**送出（`send_viewport_cmd_to` + `request_repaint`，探针那条线程实测 t=16s 心跳就回来了）。这正好是真应用里天然的位置（`jobs.rs` 那条 `try_send` 就在完成线程上），**但 `try_send` 只把消息放进通道，帧循环醒没醒要看有没有 `request_repaint`**——这一句是 D-21/D-25 那两次的同族教训，写在这里。

**不许新增唤回方式**：中间那档（主窗收进托盘）能选，但走 `mode::hide`/`mode::reveal` 既有那对函数——那套"叫得回来"的判定在 D-21（泵挂错钩子）与 D-25（叫了班没人读）上各踩过一次，本包再开第三条路就是第三次。

**恢复失败不许半死不活**：发不回（拿不到句柄）时 SHALL 照常完成截图，窗口留在收起态并给一句提示，**SHALL NOT 因为恢复失败就把截好的图丢掉**。这条与 D-25 同族：动作发出去了要有人读，恢复失败也要给结果留活路。

**验证**：无头——`prepare()` 记下/`restore()` 发回的那一组只剩"置顶 + 可见"两条（一条纯函数断言：给同一组输入两次，发回的命令序列相同）、**恢复那一段 SHALL NOT 依赖帧循环里的计时器**（静态核查：`restore()` 的调用点在子进程完成回调那条链上，不在 `ui()`/`logic()` 里）。真机——W-5.8 只看两件事：**第二次框选时"自家窗消失又回来"这一下能不能接受**、**回来位置对不对**。**"到底进没进图"这一问我们已自取正负对照（事实 32 → V-019），W-5.8 不再替它背书。**

## REQ-011 实现与验证

**口径按本包收窄**（不照抄 P6 那句"识别期间零外发"）：截图像素、历史文件、解码、识别、回填、复制/保存全程本地；`screencapture` 是系统二进制，不经任何网络；**文本经 P3 通道送出去只发生在用户按下那颗「翻译」之后**——本包没有自动翻译，所以这条比 v0.1 更简单也更严格：任何"截图后自动出网"的实现都是错的。
