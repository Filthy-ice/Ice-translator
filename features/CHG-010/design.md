## 关键决定

**1. 冻结帧由系统二进制给，不由我们自己抓。** `screencapture -x -o` 是静默整屏、实测 80～150 毫秒；自己走 ScreenCaptureKit 要引新依赖、要处理权限弹窗归属（H2 那一格 CHG-009 还没量过），而"抓一张全屏"这件事它已经做得够快。本包换掉的是**选区那一半**，不是抓屏那一半。

**2. 遮罩是「每块屏一扇」无边框窗，显示的是那块屏的冻结帧。** 压暗用整屏一张冻结图 + 选区那块按原亮度重画（`Painter::image` 的 uv 是**归一化 0..1**，不是像素坐标——事实 13 那处自纠错就是这么来的）；不需要鼠标穿透，也不需要透明窗口（透明窗 + 点击穿透正是 D-29 那一类"属性副作用没在同一扇窗上验"的坑）。开几扇的理由不是"好看"：他机器上第二块屏就在左边（事实 10），只盖主屏的话另一块仍然可点，"桌面不可操作"这句就是假话。

**3. 抓完立刻还原自家窗。** 遮罩不透明，还原在遮罩底下发生，用户看不见；而"截完图界面没回来"那一族缺陷少一条发生路径。这一条要 H5 证：遮罩与主窗同属置顶档时**谁在上面**（如果主窗盖住遮罩，顺序就得换成"先遮罩后还原"，重测）。

**4. 确认之前不落盘。** CHG-009 是"框完即写历史"，因为系统工具松手就结束了、我们拿不到"取消"这个信号（事实 14）。自绘层拿得到，所以盘上只该留下用户确认过的东西——这是隐私口径的**收紧**，不是放宽，`docs/01` NFR-3 那句要跟着改。

**5. 点 → 物理像素的换算只有一处**（`selection.rs` 里裁那一下），沿用 CHG-009 事实 22 那条纪律：两处各除一次或都忘了除，就是"裁出来的比框的大一倍"。Retina 那一档（H4）本机量不到，与 CHG-009 的 W-5.7 共用一块屏。

**6. 遮罩必须原生抬层，且抬完要读回来。** 实测三档台阶（事实 8）：原样建窗被 AppKit 夹进 `visibleFrame`（`0,63,1920x953`）；只发 `OuterPosition`+`InnerSize` 变成 `0,31,1920x1080` 但层级仍是 3，**Dock 那条采样到的是 Dock 的活画面**；只有 `setLevel(mainMenu+1)` + `setFrame(该屏 frame)` 才拿到 `layer=25 bounds=0,0,1920x1080`，抬层后再拖那两条系统条带都能出选区。这一跳的代价与配套纪律一起写：**抬完必须把 AppKit 实际给的矩形读回来**当坐标基准——拿"我请求的矩形"去换算，出的就是"裁出来的图整体偏 63 像素"这一类查不出根的缺陷（与 CHG-009 事实 22 的 `ppp` 那条同源）。SHALL NOT 用 `Fullscreen(true)` 顶替：切 Space + 动画，为截图这一件事动系统级状态不值。

**7. esc 的开关是"应用激活"，而激活是异步的。** 事实 16 把机制那一半定死了：不激活 ⇒ `key=false`、注入 esc **一条 Key 事件都进不来**；把应用提到前台 ⇒ `active=true key=true`、esc 进得来。同一段代码两次读数的差就是"要不要抢焦点"这一个动作，所以 Q-006 剩下的只是取舍。实现侧跟着定死两条：① 取消的**主入口是动作条那颗「取消」**（点遮罩外也算），esc 是附加；② 若他选"激活"那一档，**SHALL NOT 写"发一次 `activate` 就当成功"**——探针读到的事实是发出去那一刻 `active=false`、约 0.15 秒后才 `true`，要下一帧核对（这与事实 41 那条"回调叫了循环才算送到"是同一族：动作发了 ≠ 状态变了）。鼠标与键盘是两条独立的路，"点得中"推不出"按得动"（D-29 那句话第 N 次应验，事实 9 与事实 16 各证一遍）。

**8. 每块屏一扇遮罩，两块屏的缺口本来就不一样大。** 事实 15：第二扇遮罩开在左边那块屏上，同样要先被夹成 `-1920,-120,1920x1137`、再靠抬层与对位才拿到 `layer=25 bounds=-1920,0,1920x1200`。两条写法约束由此而来：① **抬层与对位那一步要按"这一块屏"做**，SHALL NOT 拿主屏那组常量（上让 31、下让 64）去套第二块屏——第二块屏的 `visibleFrame` 就等于 `frame`，它上面没有菜单栏可让；② 位置给的是**全局点坐标**，负 x 直接用（与 CHG-009 事实 34 那条"副屏在左、负 x 不是 bug"对上），但**读回来的也必须是被夹之前的那一个来源**（`ViewportInfo::outer_rect`），换算与命中都从它推。

**9. 同一处抬层也管贴图窗（缺陷 D-30）。** 事实 8 那组层级读数不是遮罩独有的：贴图窗同样是 `layer=3`，Dock 是 `layer=20`，所以钉到屏幕下缘的贴图会被 Dock 盖住一截。抬层入口因此收一个"要盖住整屏"的窗口列表，遮罩与贴图都从这一处走，**不开第二处 `setLevel`**；验收按事实 4 的口径在**同一扇贴图窗**上把点击、右键、esc、空格、拖窗、不被 Dock 盖这六件一次验完（D-29 就是这么犯的，别再犯第三次）。

**11. esc 这一格由用户答复定死：开遮罩即激活。** 事实 9/16 说明键盘进不进得来只取决于应用是否前台，而他 2026-11-09 晚明确要 esc 能退出 ⇒ 打开遮罩那一步要把应用提到前台。三条实现约束由此来：① **激活是异步的**（第六轮复测 `key=false` 读了约 0.1 秒才 `true`），SHALL 下一帧核对这扇遮罩是不是键盘窗，不符就重发；② 按钮与"点遮罩外"**不许因为 esc 能用了就被删掉**——抢焦点那几百毫秒里按钮是唯一退路；③ 收尾（确认或取消）之后焦点回不回得去他原来那个应用，**第六轮那一读被日志竞态吃掉了，实施第一条补测**（`HIDE-APP` 那条），测出来是什么就照实写进界面说明，不许当成"应该会回"。

**12. 认窗给的是矩形，而 mac 的圆角让矩形不等于内容。** 事实 17/18 两条读数放一起就是这一格的全部形状：系统直接给矩形（不用比对比度），而"按窗口号抓那一窗自己的像素"拿到的是**四角 alpha=0** 的 RGBA，按矩形从冻结帧裁则角上带背景。默认走矩形那条（像素来源唯一），按窗号那条挂在 Q-007 由他定；**两条不许同时留在仓里当两条裁剪路径**——来源可以两个、裁与落盘的链只能一条（停止条件 7）。

**10. 动作条复用既有接缝**：复制走 `clipboard::write_image`、保存走 `panel::request_save` + `export::save`，与本包之外的那两条链共用同一把函数（CHG-009 的"复用而不是新造"原样继承）。

## REQ-101 实现与验证

顺序是这条 REQ 的全部：**收起自家窗 → 抓整屏 → 立刻放回 → 开遮罩 → 抬层并读回几何**。前四段都短：隐藏与还原是既有的两条命令（CHG-009 事实 32），抓屏是 80～150 毫秒的子进程（事实 1，遮罩存在时复测仍是 0.07~0.09 秒，事实 12），遮罩是每帧 show 的 deferred viewport（事实 3/5）。第五段是 v0.2 新加的：**那一次原生抬层**（事实 8）。

**还原为什么放在抓完之后、而不是框完之后**：遮罩显示的是不透明的冻结图，还原在它底下发生，用户看不见。**这条已从"猜"升格成"量出来的"**（事实 7）：遮罩开着时把主窗 `Visible(false)` 再 `Visible(true)`，三个时刻各抓一次整屏，同一批采样点逐点相同，主窗那块洋红一次都没冒出来。停止条件 2 由此排除。

**抬层为什么算 REQ-101 的一步而不是 REQ-102 的装饰**：不抬层的话遮罩只有 `visibleFrame` 那块（实测 `0,63,1920x953`），菜单栏与 Dock 那两条是活的——"触发即冻结"这句话就漏了两条带。抬层与对位只能在主线程做、且**必须把 AppKit 实际给的矩形读回来**（三轮探针读到的 AppKit frame 从 `0,-31,1920x1080` 变成 `0,0,1920x1080`；不读回来就会拿请求值换算，裁出来整体偏 63 像素）。

验证：无头锁"抓屏走 spawn_blocking、失败三态各有一句能行动的话、不打开空白遮罩、抬层那一步失败时退回哪一档"；H1/H5 已由探针闭合（V-005），实施时在真应用里复核一遍（探针是裸进程，真应用有托盘与多形态窗——停止条件 5）；遮罩期间桌面**真的不可操作**这一条只有他按得出来（W-6.1）。

## REQ-102 实现与验证

选区状态机与几何**全是纯函数**：输入是"这块屏的矩形 + 一个点"，一次按下落在哪（空白 / 框内 / 八个把手里的哪一个）由一处判定，输出是新的选区矩形（已夹在该屏范围内）。这是本包唯一能被无头锁死的一大块，也是 T-002 的全部内容。**三条判定已由探针各量到一次**（事实 6）：把手只动那一个角（`900,637 → 1012,731,1162,856`）、框内移动尺寸不变、拖出屏外夹在 `1920,1080` 上。

**每块屏一扇遮罩**（事实 10：他机器上第二块屏就在左边，`1920×1200` 挂在 `(-1920,-120)`，比主屏还高 120 像素）。选区**只在一块屏内成立**，跨屏合并默认不做（Q-004）。多屏带来的不是新逻辑而是新输入：屏幕表、每屏那块的矩形、以及"按下落在哪块屏"。第二块屏那条 `y=-120` 的负偏移是真实读数，无头用例 SHALL 用它，不许拿"原点总是 0,0"当默认。

**点与物理像素只在一处换算**（裁那一下）。CHG-009 事实 22 已经因为"在线屏 ppp=1.0、看着 1:1 像是普遍规律"错过一次；本包同样有这一档（H4），本机在线两屏 `scale` 都是 1.0，**还是量不到，不许拿 1.0 的读数冒充 2.0**。

**压暗与出图**用整屏一张冻结图 + 选区那块按原亮度重画（`Painter::image`，uv 是归一化 0..1——事实 13 那处自纠错的落点）。不需要透明窗口，也不需要鼠标穿透：这两个都是 D-29 那一类坑（属性副作用没在同一扇窗上验），能不用就不用。

## 追加：每块屏的冻结帧怎么来（2026-11-09 实施时量到，不改已批准的行为）

批准之后要实现 REQ-102 那句"每块屏各一扇遮罩"，才发现"抓一张全屏"这件事本身有屏幕数依赖，三条实测：

1. **不带屏幕参数的静默抓图只给主屏**：本机实测 `screencapture -x -o -t png base.png` 产出 **1920×1080 一张**，左边那块 1920×1200 根本不在里面 ⇒ 第二扇遮罩会拿不到自己的画面。点名要用 `-D<序号>`，实测 `-D1`→1920×1080、`-D2`→1920×1200，两块各抓一次总耗时 **0.216 秒**（与单张同级，不抬高一个量级）。
2. **区域法 `-R` 不接受负坐标**（实测报 `-R requires a valid rect`），而本机第二块屏就挂在 `(-1920,-120)` ⇒ "按屏切区域"那条路在副屏上直接不通，只能走 `-D`。
3. **`-D` 的序号与我们的屏幕列表怎么对上**：按位置绑（第 i 块屏 ↔ `-D(i+1)`），并用**像素尺寸回核**（本机两屏尺寸不同，一核对就成）。两屏**像素尺寸完全相同**时这一核对无从分辨，此时 SHALL 退回"只盖主屏 + 一句说明"，SHALL NOT 猜一个把另一块的画面摆到这块屏上——那是 REQ-101 明令禁止的"打开一扇错内容的遮罩"。

规格里那句"静默整屏抓一张 → 打开全屏遮罩"因此实现成"按屏各抓一张 → 各开一扇遮罩"，失败面与原口径一致（给一句能行动的话、不开空白遮罩）；`-D` 那一条也仍然只有 `system/capture.rs` 一处字面量（V-004 那条静态核查原样成立）。
