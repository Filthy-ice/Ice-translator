# CHG-004 T-001：三条 HYPOTHESIS 的真机判定（2026-10-22）

探针：`crates/ice-app/examples/viewport_probe.rs`（一次性，不进正式产物）
原始日志：`T-001-probe.log`（v1，H1/H2/H3 首测）、`T-001-probe-v2.log`（v2，A2 降频对照 + 策略 C 单向）、`T-001-probe-v3.log`（v3，策略 C 双向对称 + 瞬移对照）
用户肉眼结论（2026-10-22 会话原话）："第一项可以，第二项测试缩小时一卡一卡的，不是平滑变形，ppt了已经，恢复全量尺寸时更是没有动画，直接卡到大，第三项通过。" / "InnerSize还是有点卡，复原还是直接卡到大，补间现在很丝滑。" / "不行，返回全量也要有动画。" / "算了不要动画了，都做成瞬间的。"

## H1 无边框 + `Resizable(true)` 能边缘缩放 —— 成立

v1 日志 `frame=64…108`（06:39:09.317→09.681）：用户拖角期间 inner 从 651×437 连续变到 831×549，
相邻两帧间隔稳定在 16ms 左右，共 20+ 个离散尺寸台阶，无一帧丢失。

结论：AppKit 在 `NSWindowStyleMask::Resizable` 单独打开（Titled 不给）时**保留原生边缘缩放热区**，
且用户驱动的缩放本身是 60fps 平滑的。REQ-001 的"走 AppKit 原生边缘缩放、不自绘手柄"可行，
停止条件 1 不触发。

## H2 逐帧 `InnerSize` 补间 —— **不成立**，且设计里的第一级降级（30fps）也不成立

两次独立实测，两种频率，同一个失败形态：

| 跑次 | 频率 | 补间耗时 | 窗口真正拿到的尺寸台阶 | 冻结 |
|---|---|---|---|---|
| v1 06:39:25 | 每帧（~60fps 发命令） | 212ms | 命令发了 14 条，`geom` 只落 4~5 个台阶 | 无（但台阶太少） |
| v1 06:39:51 | 每帧 | **1006ms** | 593×336 之后直接跳 460×96 | **frame=1403@51.190 → frame=1404@52.196** |
| v1 06:39:57 | 每帧 | **1026ms** | 同上 | **frame=1533@57.435 → frame=1534@58.461** |
| v2 07:14:13 | 30fps | 211ms | 4 个台阶（625×394 / 579×311 / 498×164 / 460×97） | 无 |
| v2 07:14:27 | 30fps | 229ms | 4 个台阶（608×362 / 535×232 / 472×118 / 460×96） | 无 |
| v2 07:27:13 | 30fps | **1086ms** | 606×360 之后直接跳 460×96 | **t=0.276@13.171 → t=5.431@14.202** |

机制：`ViewportCommand::InnerSize` 走 `request_inner_size`，是异步请求；egui 下一帧读到的
`inner_rect` 才是真值。实测**每 200ms 只有 4~5 次请求真正落到窗口上**，而且约 1/3 的跑次里
整个事件循环停摆 ~1.0 秒（三次复现，1006/1026/1086ms，都发生在窗口缩小过程中）。
用户看到的就是"卡一卡 + 中途僵住 + 最后一下跳到终点"。

设计里写的第一级降级（补间频率降到 30fps）已被 v2 直接否掉：冻结照样复现，台阶数没有改善。
"只补间尺寸不补间位置"本来就是探针的做法（outer 全程 (200,160) 不变），也不成立。
→ 停止条件 3 触发。

## H3 窗口级 `with_transparent(true)` —— 成立

v1/v2 全程窗口透明：无黑底、无花屏、无圆角异常；失焦（`focused=false`，07:14:32 / 07:27:25）
后画面无变化；用户肉眼判定"第三项通过"。停止条件 2 不触发，REQ-007 走窗口级半透明、
不需要降级成内容级 `Ui::set_opacity`。

附带收益：透明可用是策略 C 的前提（见下）。

## 替代方案 C：窗内补间（窗口几何整段只动一次）—— 实测丝滑

v2 07:27:22 那次（从 640×420 补间到 460×96）：

- 绘制帧 14 帧 / 204ms，节奏 16.5ms ± 1ms（**真 60fps**）；
- 面板尺寸单调下降 640×420 → 635×410 → 623×390 → … → 462×100 → 460×96，无回跳、无停顿；
- **动画全程窗口几何一动不动**（每帧日志的 `window=640x420` 恒定）；
- 收尾只发一条 `InnerSize(460×96)`，26ms 后 `geom frame=2430 inner=460x96` 落定，误差 0px。

用户结论："补间现在很丝滑。"

原理：动画期间窗口比可见内容大，多出来的是透明区（H3 已证可用），所以看不见；
补间的是画在窗口里的内容矩形，走的是 egui 自己的绘制循环，不经过 AppKit 的异步 resize 往返，
因此不受 H2 那个 4~5 台阶 + 1 秒停摆的限制。

代价（必须在 REQ-004 里写明，不能藏）：

1. 动画期间透明区仍属于本窗口，会吞掉那 200ms 内落在透明区的点击（不做 per-region 穿透）；
2. 动画期间窗口矩形 ≠ 可见矩形，若系统给窗口画阴影，阴影会跟着大矩形走
   （winit 只在 `platform_specific.has_shadow = false` 时才 `setHasShadow(false)`，
   见 `winit-0.30.13/src/platform_impl/macos/window_delegate.rs:626-628`；egui 的
   `ViewportBuilder` 不暴露这一项，需要时用 objc2 直接关）；
3. 收尾那一次几何变更是"瞬时"的，肉眼能否察觉取决于内容是否已经画到位——
   实测未察觉，但必须留一条走查项（W-2.14）专门盯这一下。

"复原直接卡到大"不是缺陷：v2 的「复原 640×420」按钮本来就只发一条 `InnerSize`、没有补间，
它顺带证明了**单条几何命令是瞬时落定的**（这正是策略 C 收尾能藏住的原因）。

## 判定汇总

| 假设 | 结论 | 处置 |
|---|---|---|
| H1 无边框边缘缩放 | 成立 | 按 REQ-001 原方案实现 |
| H2 逐帧 InnerSize 补间 | **不成立**（30fps 降级亦不成立） | 停止条件 3 触发：记 `SPEC_DEVIATION`，REQ-004 的机制改为策略 C，交用户重新批准 |
| H3 窗口级半透明 | 成立 | 按 REQ-007 原方案实现 |

FR-3.9 的**行为**要求（180~220ms、同一窗口、无跳变无黑屏无闪烁、端点 ±2px、动画期间可点击、
可反向插值）在策略 C 下全部保留；变的是实现机制，不是需求，也不是 Must 降级。

## v3 追加实测（2026-10-22 09:24）：C 的"外接矩形"变体同样撞 1 秒停摆

上面 §C 的结论有一个隐含前提，v2 没有暴露出来：**动画全程窗口几何一动不动**（v2 只在收尾缩一次）。
用户随后指出"返回全量也要有动画"，v3 因此把 C 做成双向对称：起点先发一条命令把窗口设成两端 rect 的
**外接矩形**（1160×636，透明故不可见），再在窗口内插值内容矩形，末帧收到精确终点。
结果这个变体**不成立**——冻结原样复现，而且每次必现：

| 跑次 | 方向 | 内容帧数 | 实际用时 | 冻结 |
|---|---|---|---|---|
| 09:24:43 | 全量 → 简洁 | 4 帧 | **1027ms** | frame=85 t=0.119@43.772 → frame=86 t=5.134@44.775 |
| 09:24:47 | 简洁 → 全量 | 3 帧 | **1028ms** | frame=236 t=0.061@47.153 → frame=237 t=5.138@48.168 |
| 09:24:54 | 460×96 → 460×96（外接矩形 = 自身，窗口不resize） | 13 帧 | 203ms | **无**，节奏 16.5ms |
| 09:24:56 | 简洁 → 全量 | 3 帧 | **1042ms** | frame=582 t=0.164@56.511 → frame=583 t=5.210@57.520 |

对照项（同一次运行里的「瞬移」按钮，单发 `InnerSize`+`OuterPosition`）：
`09:24:51.289 发命令 → 09:24:51.309 geom 落定`，**20ms，一步到位，无停摆**。

机制修正：1 秒停摆的触发条件不是"命令发得多频繁"，而是**窗口 surface 真的被 resize**。
第三行那次跑（外接矩形恰好等于当前 rect，一条几何命令都没让窗口变尺寸）13 帧满速跑完，
说明插值本身、透明绘制、`request_repaint` 循环都不慢；只要窗口尺寸一变，事件循环就停 ~1.0s。
这也解释了 v2 为什么"丝滑"：它整段没有 resize；也解释了 v1/v2 的冻结为什么"都发生在窗口缩小过程中"。

→ 双向 C 要成立，就得在动画起点把窗口撑成外接矩形，而这一次撑大必然带来 1 秒停摆。
**策略 C 只能做单向（大 → 小，起点不 resize），做不了对称的双向形变。**

## 用户决定（2026-10-22）：取消动画，两个方向都做瞬时切换

用户原话："算了不要动画了，都做成瞬间的。"

这走的是 Spec 停止条件 8 里"改需求"那一支（不是"退回硬切"那一支——两者在这里已经合流：
硬切就是瞬时切换）。FR-3.9 由"180~220ms 形变动画"改为"同一窗口的瞬时切换"，
Must 级别与编号保留，保留下来的可测部分是：不重建窗口、不黑屏不闪烁、内容不丢、端点 ±2px、
切换后立即可交互。`ice-app::mode::Morph` 不再实现。
